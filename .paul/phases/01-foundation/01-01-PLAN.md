<objective>
## Goal
Add fixed-window rate limiting to all `/api/*` routes via Next.js middleware, backed by a new D1 table — protecting auth endpoints (10 req/min) and general API endpoints (60 req/min) per IP.

## Purpose
Auth endpoints (login, register) are currently unprotected against brute force. This is the first security layer before billing and plan gating are built — a prerequisite for any paid production traffic.

## Output
- `migrations/002_rate_limit_buckets.sql` — new D1 table
- `schema.sql` — updated master schema
- `src/lib/rate-limit.ts` — reusable fixed-window rate limiter utility
- `src/middleware.ts` — Next.js middleware applying limits, failing open on error
</objective>

<acceptance_criteria>

## AC-1: Auth endpoints are rate limited
```gherkin
Given a client making POST requests to /api/auth/login or /api/auth/register
When they send more than 10 requests within a 60-second window from the same IP
Then the endpoint returns 429 with a Retry-After header
And subsequent requests within the window continue to return 429
```

## AC-2: General API endpoints are rate limited
```gherkin
Given a client making requests to any /api/* route (excluding auth group)
When they exceed 60 requests within a 60-second window from the same IP
Then the endpoint returns 429 with a Retry-After header
```

## AC-3: Rate limit headers are present on all API responses
```gherkin
Given any request to /api/*
When the request is within limits
Then the response includes X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset headers
```

## AC-4: Middleware fails open
```gherkin
Given the D1 database is unavailable or throws an error
When the middleware catches the error
Then the request is allowed through (NextResponse.next())
And the error is logged to console
```

      key TEXT PRIMARY KEY,           -- format: "{ip}:{group}" e.g. "1.2.3.4:auth"
      count INTEGER NOT NULL DEFAULT 1,
      window_start INTEGER NOT NULL   -- Unix timestamp (seconds), aligned to window boundary

<task type="auto">
  <name>Task 2: Rate limiter utility — src/lib/rate-limit.ts</name>
  <files>src/lib/rate-limit.ts</files>
  <action>
    Create `src/lib/rate-limit.ts` — a self-contained fixed-window rate limiter
    that accepts a D1Database directly (does NOT use the singleton from db.ts).

    Export:
    ```ts
    export interface RateLimitResult {
      allowed: boolean;
      remaining: number;
      resetAt: number; // Unix seconds
    }

    export async function checkRateLimit(
      db: D1Database,
      key: string,
      limit: number,
      windowSecs: number
    ): Promise<RateLimitResult>
    ```

    Implementation:
    1. Compute `windowStart = Math.floor(Date.now() / 1000 / windowSecs) * windowSecs`
    2. Use D1 batch() to run two statements atomically:
       - Statement 1 (upsert):
         ```sql
         INSERT INTO rate_limit_buckets (key, count, window_start)
         VALUES (?, 1, ?)
         ON CONFLICT(key) DO UPDATE SET
           count = CASE WHEN window_start = excluded.window_start
                        THEN count + 1
                        ELSE 1 END,
           window_start = excluded.window_start
         ```
         Bound with: [key, windowStart]
       - Statement 2 (read back):
         ```sql
         SELECT count, window_start FROM rate_limit_buckets WHERE key = ?
         ```
         Bound with: [key]
    3. Read `count` from batch result[1].results[0]
    4. Return:
       - `allowed`: count <= limit
       - `remaining`: Math.max(0, limit - count)
       - `resetAt`: windowStart + windowSecs

    Avoid: using the db.ts singleton helpers — accept D1Database directly for middleware independence.
    Avoid: any Node.js-only APIs — use only Web APIs and D1.
  </action>
  <verify>npx tsc --noEmit (no TypeScript errors in rate-limit.ts)</verify>
  <done>AC-1, AC-2 mechanism implemented: checkRateLimit correctly increments and checks fixed-window counters</done>
</task>

<task type="auto">
  <name>Task 3: Next.js middleware — src/middleware.ts</name>
  <files>src/middleware.ts</files>
  <action>
    Create `src/middleware.ts` at the project src root.

    Logic:
    1. Get D1 binding via `getCloudflareContext({ async: true })` from `@opennextjs/cloudflare`
    2. Extract client IP from `cf-connecting-ip` header (Cloudflare sets this),
       fall back to `x-forwarded-for` first value, then `'unknown'`
    3. Classify route:
       - Auth group (strict): pathname starts with `/api/auth/login` or `/api/auth/register`
         → limit = 10, key = `${ip}:auth`
       - General API: everything else matching `/api/*`
         → limit = 60, key = `${ip}:api`
    4. Call `checkRateLimit(db, key, limit, 60)`
    5. If NOT allowed: return `new NextResponse('Too Many Requests', { status: 429 })`
       with headers:
       - `Retry-After`: seconds until resetAt
       - `X-RateLimit-Limit`: limit
       - `X-RateLimit-Remaining`: '0'
       - `X-RateLimit-Reset`: resetAt
    6. If allowed: return `NextResponse.next()` with headers:
       - `X-RateLimit-Limit`: limit
       - `X-RateLimit-Remaining`: remaining
       - `X-RateLimit-Reset`: resetAt
    7. Wrap entire logic in try/catch — on any error, log and return `NextResponse.next()`
       (fail open — never block requests due to rate limiter failure)

    Export config matcher:
    ```ts
    export const config = {
      matcher: ['/api/:path*'],
    };
    ```

    Avoid: importing from src/lib/db.ts (rate limiter is middleware-independent)
    Avoid: blocking requests when D1 is unavailable (fail open is intentional)
  </action>
  <verify>
    npx tsc --noEmit

    Expected: first 10 return 400 or 401, 11th returns 429
  </verify>
  <done>AC-1, AC-2, AC-3, AC-4 satisfied: middleware applies rate limits and fails open on error</done>
